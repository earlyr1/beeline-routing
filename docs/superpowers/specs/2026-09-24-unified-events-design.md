# Единый поток событий дня, окно выбора по результату и событие «Коммуникация»

Дата: 2026-09-24. Заменяет в части «какие события ломающие» спецификацию
`2026-09-17-event-variants-design.md`; стратегии optimal / stable / keep / assign:<бригада> остаются.

## Зачем

Ответ организаторов: перестраивать маршруты посреди дня (в том числе чужих бригад) можно после любого
изменения — параметры заявки, болезнь, задержка, смена транспорта, ручное переназначение; при форс-мажоре можно
вызвать бригаду с выходного. Сейчас события поделены на классы (BREAKING_EVENTS, VARIANT_EVENTS, is_choosable,
takes_variant, is_assignable), а в планировании около десятка веток по типу события. Цель — один поток для
всех событий и как можно меньше if/else по типу.

## Решения пользователя (зафиксированы в разговоре)

1. Все события идут одним путём: «что изменилось в фактах дня» → закрепить сделанное → посчитать варианты →
   решить, нужно ли окно выбора → сохранить шаг. Наборов «ломающих» событий больше нет.
2. Окно выбора открывается ПО РЕЗУЛЬТАТУ, а не по типу (правило Б): если у «Ничего не менять» поломок больше,
   чем у лучшего из пересчётов («Оптимально по дню», «Минимум перестановок»). Иначе шаг молча применяется с
   «Ничего не менять», а сменить вариант диспетчер может через «Варианты…» на шкале.
3. «Ничего не менять» — честное «ничего»: чужие маршруты как есть, осиротевшие заявки (новая срочная, снятые
   с выбывшего инженера и т. п.) остаются без инженера. Единственное, что делает сам факт события: заявка,
   закреплённая за бригадой (fixed_engineer_id — переназначение диспетчера), встаёт в маршрут этой бригады
   (сегодняшний insert_plan). Это общее правило для всех закреплённых заявок, без проверки типа события.
4. Бригада «с выходного» отдельной механики не получает: бригады дня, которых нет в утреннем плане, решатель
   и так берёт за полную цену vehicle_fixed_cost (работавшие сегодня — бесплатно, ortools_solver.py). Цена сама
   определяет форс-мажор. В коде ничего не меняется, только README.
5. Новый тип события «Коммуникация» (client_agreed): отметка ✓ во вкладке «Коммуникации» становится событием
   на шкале вместо отдельного хранилища agreed.
   - «Приедем в окно X»: у заявки окно становится X (не asap), решатель обязан его держать.
   - «Сегодня не приедем»: заявка получает статус «перенесена» (postponed). Решатель её не получает и не
     пытается пристроить, но в плане она остаётся среди «Без инженера» с причиной «Перенесена, клиенту
     сообщили» и считается в метрике «Не назначено» (это наш провал, метрика должна его показывать).
   - «Клиент отказался» остаётся обычной отменой (cancel).
   - Время события — время на часах в момент отметки. Снять ✓ — удалить событие со шкалы.
   - Таблица agreed_windows, эндпоинты PUT/DELETE /agreed/{request_id} и поле version отметки больше не нужны:
     перемотка часов работает как у всех событий. Миграция старых сохранённых дней не нужна.

## Часть 1. Единый поток и правило Б

### Слой «что изменилось» (единственное место, где важен тип события)

Новый модуль (например `backend/app/planning/facts.py`) с таблицей обработчиков `EventType → функция`.
Обработчик получает сессию, событие, контекст; проверяет событие (EventRejected с теми же текстами, что сейчас)
и возвращает результат одного вида, например:

- requests, engineers — изменённые копии;
- stored_event — событие с полями, которые заполняет backend (previous_request и т. п.);
- released — номера заявок, которые надо открепить от текущего плана (сейчас это делает _pinned_problem для
  request_updated и request_reassigned);
- subject_request_id — заявка, о которой событие, если оно об одной заявке (для стратегии «отдать бригаде»);
- при необходимости — поправка задачи (задержка инженера: delay_engineer / missed_hold) и подпись к diff
  (прогноз задержки forecast_delay). Форма на усмотрение реализации, но так, чтобы apply_event, _pinned_problem,
  timeline и routes не содержали проверок EventType.

Сегодняшняя логика `_changed_inputs` переезжает в обработчики без изменения поведения и текстов ошибок.

### Планирование

- `apply_event(session, event, ctx, variant)` — одинаков для всех типов: обработчик фактов → _release_pins →
  стратегия assign (если variant = assign:<id> и у события есть subject_request_id активной заявки) →
  day_problem → закрепление сделанного (+ released, + поправка задачи) → keep_plan или решатель → diff →
  подпись к diff → новая сессия. share пула: 2 всегда (optimal и stable считаются вместе).
- Проверка достижимости при переназначении (_check_reachable) — часть обработчика переназначения или общая
  проверка «закреплённая заявка достижима для своей бригады»; не ветка по типу в apply_event.
- `keep_plan` объединяется с `insert_plan`: прежние маршруты, каждая закреплённая заявка, которой нет в
  маршруте её бригады, вставляется в него (как insert_plan сейчас: бригада пропускает то, на что не успевает);
  всё остальное как у keep_plan сейчас. Особые названия у переназначения («Вставить в маршрут») убираются —
  у всех событий «Ничего не менять» / «Оставить маршруты как есть»; допустима общая подсказка вроде
  «Только само событие, остальные маршруты как есть».
- Стратегия «отдать бригаде» (assign:<id>) доступна любому событию с subject_request_id, заявка которого после
  события активна (не отменена и не перенесена).
- Из `variants.py` уходят BREAKING_EVENTS, VARIANT_EVENTS, is_choosable, takes_variant, is_assignable,
  EVENT_VARIANT_TITLES, EVENT_VARIANT_SUMMARIES, INSERT_*; choice_request_id заменяется subject_request_id.

### Правило Б: нужен ли выбор

Функция вида `needs_choice(outcomes) -> bool` в variants.py:
поломки(plan) = заявки без инженера (plan.unassigned, кроме перенесённых — они одинаковы во всех вариантах)
+ визиты с опозданием (late_visits) + визиты/маршруты за концом смены (если такое считается в плане).
Выбор нужен, если поломки(keep) > min(поломки(optimal), поломки(stable)). Если optimal отклонён — событие
отклонено, как сейчас.

### Шкала (backend/app/planning/timeline.py, backend/app/api/timeline.py)

- У записи шкалы variant = None значит «диспетчер не выбирал». Для такой записи считаются все три базовые
  стратегии (как _replay_variants сейчас для «ломающих»). В walk(): если посчитаны все три и needs_choice —
  запись становится awaiting (часы встают, окно выбора); если выбор не нужен — проход идёт по шагу keep
  (ключ entry@keep), без остановки. Решение пересчитывается при каждом проходе, поэтому после вставки
  более раннего события оно может поменяться.
- Явный variant у записи (выбор диспетчера, кнопки «Коммуникаций», API) — как сейчас.
- `/datasets/{id}/events` и помощник (`app/api/proposals.py`) ставят variant="optimal" любому событию
  (сохраняется нынешнее поведение: без окна).
- `event_choice` и `check_variant` работают для любого события (нет 409 «событие без вариантов»), кроме
  отклонённого.
- TimelineItem: поле choosable убрать или сделать true для всех; добавить признак, что вариант выбран
  автоматически (например `variant_auto: bool` и variant = "keep"), чтобы шкала писала «Вариант: Ничего не
  менять — выбирать было не из чего» (формулировка на усмотрение, коротко).
- Предподсчёт шкалы (ensure_precompute) считает три стратегии для каждого события без выбора.

### Фронтенд

- «Варианты…» доступны у любого неотклонённого события на шкале.
- Окно выбора открывается по pending_choice из ответа сервера — для любого типа события (правка заявки,
  отмена из карточки после 5-секундного уведомления и т. д.). Проверить, что диалоги правки, отмены, задержки,
  транспорта, недоступности, переназначения корректно переживают ответ с pending_choice.
- Кнопки «Коммуникаций» «Отменить и пересчитать остаток дня» (optimal) и «Отменить, маршруты не трогать»
  (keep) — явный variant, как сейчас.
- Тексты и подписи про «ломающие» события, «без окна вариантов» и т. п. привести к новой логике.

### Тесты

Существующие тесты, которые фиксируют старую классификацию (например «правка заявки пересчитывается без окна»,
«отмена не открывает окно»), переписать под правило Б. Новые тесты минимум:
- needs_choice: поломки keep > лучшего → True; равны → False;
- срочная заявка → окно (keep оставляет её без инженера);
- мелкая правка заявки, которую маршрут переживает без опозданий → нет окна, применён keep, variant_auto;
- отмена без брошенных заявок → нет окна; отмена, когда есть брошенные заявки, которые освободившаяся
  бригада может взять → окно;
- переназначение с keep → заявка в маршруте выбранной бригады (общее правило закреплённых заявок);
- assign доступен правке заявки, недоступен отмене;
- в apply_event / timeline / routes нет обращений к EventType (можно проверить grep-тестом или ревью).

## Часть 2. Событие «Коммуникация» (client_agreed)

- EventType.CLIENT_AGREED = "client_agreed"; поля: request_id и окно (например `agreed_window: TimeWindow | None`;
  None — «сегодня не приедем»). Валидатор Event: request_id обязателен.
- RequestStatus.POSTPONED = "postponed". Обработчик фактов: окно X → window_start/end = X, asap = False;
  None → status = POSTPONED. Проверки: заявка есть, не отменена, не уже в работе (как у правки), окно X не
  раньше времени события и начало < конца.
- Задача решателя не включает перенесённые заявки (как отменённые). Сборка плана добавляет их в
  plan.unassigned с новой причиной (ReasonCode.POSTPONED, текст «Перенесена, клиенту сообщили»), метрика
  «Не назначено» их считает. FCFS-базовый и сравнение — проверить, что «Не назначено» считается одинаково.
- Проходит тем же единым потоком и тем же правилом Б (как правило, выбор не нужен).
- PlanningState.agreed для фронтенда строится из примененных до текущего времени событий client_agreed
  (request_id → окно / null, плюс id записи шкалы, чтобы снять ✓). Хранилище agreed в repo.py / memory.py /
  postgres.py, таблица agreed_windows (новая миграция, которая её удаляет) и эндпоинты /agreed удаляются.
- Фронтенд: ✓ во вкладке «Коммуникации» отправляет событие client_agreed на шкалу (addTimelineEvent,
  время = часы); снять ✓ — deleteTimelineEvent. Логика списка звонков (lib/communications.ts) опирается на
  окно заявки после события и на agreed из состояния; обещанное окно X становится окном заявки, поэтому
  дальнейшие расхождения считаются от него. Перенесённая заявка — в блоке «уже договорились», не ждёт звонка.
- Шкала: у события свой короткий ярлык («Звонок»), в списке событий — текст вида «Клиент: окно 16:00–18:00»
  или «Клиент: сегодня не приедем».
- Помощник (LLM) этот тип не предлагает; перечисления типов в LLM-слое и на фронте не должны ломаться.
- Тесты: окно X держится решателем при следующем пересчёте; перенесённая заявка не назначается ни в одном
  варианте и считается в «Не назначено»; перемотка часов до отметки снимает её эффект; снятие ✓ удаляет событие.
