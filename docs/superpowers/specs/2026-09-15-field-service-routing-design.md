# Дизайн: сервис планирования маршрутов выездных инженеров (кейс Билайн Бизнес, ЛЦТ)

Дата: 2026-09-15. Статус: согласован. Правки 2026-09-15 после проверок в песочнице отмечены в разделе 15.

## 1. Цель и рамки

Прототип помощника диспетчера по ТЗ Билайн Бизнес (`3. Билайн Бизнес.pdf`, конспект в `research/tz-and-data-notes.md`). Демо 5-7 минут: загрузить данные, спланировать, показать карту и список, объяснить одну заявку, применить событие, показать diff, сравнить метрики с базовым вариантом.

Обязательные ограничения: навык (3 из справочника), время (окно заявки, смена, путь, длительность), тип транспорта (4 типа). Обязательные метрики: число задействованных инженеров, пробег по каждому инженеру и суммарно. Базовый вариант FCFS реализуется ровно по тексту ТЗ.

Чем бьём конкурентов: сравнение не только с FCFS, но и с реальным распределением диспетчеров из контрольного файла; инженеры и длительности синтезируются скриптом из истории, а не выдумываются; все три события, diff, таймлайн, объяснения; реальные дороги через OSRM.

Не делаем: авторизацию, БД планов, мобильное приложение, честный time-dependent VRP, учёт оборудования.

## 2. Архитектура

Три контейнера в `docker compose`:

- `frontend`: nginx, раздаёт собранный React (Vite, TypeScript), проксирует `/api` в backend. Наружу порт 8000.
- `backend`: FastAPI, Python 3.12, OR-Tools. Внутри сети на 8001. Состояние сеанса в памяти процесса, кэш матриц OSRM в SQLite (volume), кэш геокодинга в `data/geocode_cache.json` (в git). Ключ Яндекс Карт и параметры LLM через env.
- `osrm`: `ghcr.io/project-osrm/osrm-backend:v26.9.0-debian` (есть arm64), `osrm-routed --algorithm mld --max-table-size 10000`, профиль car. One-shot сервис `osrm-prepare` скачивает `central-fed-district-latest.osm.pbf` с Geofabrik (835 МБ), вырезает bbox Москвы и области через osmium и собирает граф MLD в volume; запускается отдельной командой из README.

Dev-режим без докера: Vite dev server с прокси, `uvicorn --reload`, OSRM либо в докере, либо гаверсинус-фолбэк с пометкой в отчёте предподсчёта.

Поток данных: CSV/JSON -> `ingest` (парсинг, нормализация, геокодинг) -> `Problem` -> `geo` (матрицы) -> `solvers` (FCFS и OR-Tools) -> `Plan` -> `explain` -> API -> UI. События идут в `replan`, который собирает новый `Problem` с закреплённым прошлым и вызывает тот же солвер.

## 3. Данные и синтез

### 3.1 Исходные данные
Zip от организаторов, cp1251, `;`. На регион два файла: «Контрольное распределение» (реальное распределение по бригадам, статусы) и «Синтетические данные» (те же строки, новые ID, без бригад, три мусорные строки, в одной из них адрес офиса). Нет инженеров, длительностей, координат, транспорта, приоритетов. Детали в `research/tz-and-data-notes.md`.

### 3.2 Скрипт `prepare` (оффлайн)
Вход: пара файлов региона (`data/raw/<region>_control.csv`, `data/raw/<region>_synthetic.csv`). Выход: `data/bundles/<region>/bundle.json` (модель `Bundle`: регион, офис, заявки, инженеры, демо-события, план диспетчеров) и `report.md`. Все правила в `backend/config/synth_config.yaml` с фиксированным `seed`:

- Навык заявки по типу BK: Локальная заявка -> Локальные работы; Подключение и Дозаказ -> Работы на подключение и дозаказы; Глобальная проблема -> Аварийные работы.
- Длительность: таблица по типу HD (медиана и разброс), выбор детерминированный по seed.
- Приоритет «Срочная»: аварии и заявки со статусом «Просрочена» в контроле, остальные «Обычная».
- Транспорт в заявке: по конфигу, редко, для аварий и дозаказов оборудования («Автомобиль»), чтобы ограничение реально проверялось.
- Инженеры: по одному на бригаду из контрольного файла. Навыки из истории заявок бригады, приведённые к 1-3 навыкам ТЗ. Транспорт по распределению из конфига (большинство авто, часть пешеход и общественный транспорт, один-два велосипеда). Смена одна из двух из конфига (например 09:00-18:00 и 13:00-22:00), выбор по тому, в какие часы бригада реально работала. Старт: адрес офиса региона.
- Отменённые в контроле заявки попадают в `events.json` как события отмены, аварии со статусом «Отправлена» как кандидаты в срочные.
- `control_plan.json`: распределение диспетчеров в формате `Plan`, пробег считается нашей матрицей по порядку окон.
- Самопроверка: скрипт гоняет FCFS и OR-Tools на бандле и завершается ошибкой, если FCFS не хуже хотя бы по одной обязательной метрике. Так требование ТЗ про конфликт проверяется, а не декларируется.
- Ловушки, которые скрипт обрабатывает явно и пишет в отчёт: кодировка, дубли ID, пустые строки, строка офиса, район «GPON Даниловский», окна 0:01-23:59, адреса вне Москвы (Кашира, Ступино, Домодедово).

### 3.3 Загрузка в вебе
`POST /api/upload` принимает либо сырой CSV Билайна (регион определяется по адресу офиса или по районам, берётся заранее синтезированный `engineers.json` региона), либо готовый бандл JSON по схеме ТЗ (может принести жюри). Геокодинг через Nominatim (не чаще 1 запроса в секунду) по нормализованным вариантам адреса: дом, улица, район или город. Хиты и промахи кэшируются в `data/geocode_cache.json`, файл коммитится, поэтому демо не ходит в сеть за известными адресами. Заявка без координат не планируется и получает причину `address_not_found`. Предподсчёт идёт в фоне, фронт опрашивает статус. Ответ: отчёт предподсчёта (заявок, геокодировано по точности, отброшено с причинами, регион, источник матрицы).

Открытый вопрос организаторам: один регион за загрузку или вся Москва с тремя офисами. Проектируем под один регион, модель данных не мешает объединить.

## 4. Доменная модель

Pydantic-модели в `backend/app/domain/`, они же схема JSON-бандла и API. Единицы: минуты, километры, `HH:MM`, широта и долгота.

- `Request`: `id`, `address`, `lat`, `lon`, `geocode_precision`, `district`, `duration_min`, `window_start`, `window_end`, `priority` (normal | urgent), `skill`, `transport_required` (optional), `status` (active | cancelled), `source_type_bk`, `source_type_hd`.
- `Engineer`: `id`, `name`, `start_lat`, `start_lon`, `shift_start`, `shift_end`, `skills` (1-3), `transport`, `available` (bool), `unavailable_from` (optional `HH:MM`).
- `Event`: `type` (urgent | cancel | restore | engineer_unavailable), `time`, `request` (полная заявка для urgent), `request_id`, `engineer_id`.
- `Problem`: заявки, инженеры, матрицы, `now`, закреплённые визиты, предыдущий план.
- `Visit`: `request_id`, `arrival`, `start`, `end`, `leg_km`, `leg_min`, `pinned`.
- `Route`: `engineer_id`, `visits`, `total_km`, `total_min`, `start_point`.
- `Plan`: `solver`, `routes`, `unassigned` (`request_id`, `reason_code`, `reason_text`), `metrics`, `violations`. Объяснения считаются по запросу и в план не входят.
- `Metrics`: `engineers_used`, `km_per_engineer`, `total_km`, `assigned`, `unassigned`, `violations`.
- `PlanDiff`: перемещённые между инженерами, изменившие порядок, добавленные, снятые, сдвиги времени по визитам.
- `Proposal`: `id`, `event`, `rationale`, `status` (pending | approved | rejected), `result_diff`.

## 5. Модуль `geo`

Матрицы времени и расстояния для набора точек (офис плюс заявки). Источник для автомобиля: OSRM `table` (минуты и километры). По типу транспорта:

- Автомобиль: минуты OSRM умножить на почасовой коэффициент пробок из `traffic_profile.yaml`, коэффициент выбирается по слоту окна заявки назначения. Матрица на слот.
- Велосипед: километры OSRM (маршрут как у авто) делить на 20 км/ч, без пробок.
- Пешеход: километры OSRM foot-профиля, если поднят, иначе автомобильные километры на коэффициент 1.2, скорость 5 км/ч.
- Общественный транспорт: гаверсинус на 1.3, скорость 15 км/ч, плюс 10 минут ожидания. Допущение описано в README.

Кэш матриц в SQLite по хэшу списка координат и профиля. Фолбэк без OSRM: гаверсинус на 1.3 и скорость по типу транспорта, отчёт предподсчёта помечает источник.

## 6. Солверы

Протокол `Solver.solve(problem: Problem) -> Plan`. Общая для всех реализаций проверка допустимости `feasibility.check(plan, problem)`, она же используется в тестах.

### 6.1 `fcfs`
Ровно по ТЗ: заявки в порядке входного файла, первому по порядку во входных данных инженеру, который удовлетворяет навыку, транспорту и у которого визит помещается в окно и смену с учётом пути от текущей точки. Порядок визитов равен порядку назначения. Без оптимизации.

### 6.2 `ortools`
OR-Tools RoutingModel:
- Инженер это vehicle со стартом в офисе и виртуальным концом без стоимости (возврат не требуется).
- Навык и транспорт: `VehicleVar(index).SetValues([-1, ...])` по предвычисленному списку допустимых инженеров. В Python-обёртке OR-Tools 9.15 `SetAllowedVehiclesForIndex` не принимает список, проверено.
- Окна и смены: `Time` dimension, окно на `CumulVar` узла, смена на старте и конце vehicle, ожидание разрешено.
- Пробег: `Distance` dimension, километры в стоимость дуги.
- Число инженеров: фиксированная стоимость vehicle, много больше суммарного пробега дня, чтобы метрика «меньше людей» была первичной.
- Неназначенные: `AddDisjunction` со штрафом, срочные получают штраф на порядок выше.
- Стабильность при перепланировании: штраф за визит, ушедший к другому инженеру относительно предыдущего плана.
- Поиск: `PATH_CHEAPEST_ARC` плюс `GUIDED_LOCAL_SEARCH`, лимит 3 секунды, warm start через `ReadAssignmentFromRoutes` (принимает индексы менеджера, а не номера узлов), если есть предыдущий план.

Время суток: матрица берётся по слоту окна заявки назначения, честный time-dependent проезд не моделируется. Допущение в README.

### 6.3 Метрики и сравнение
`metrics.compute(plan)` для любого плана, включая `control_plan`. Сравнение в API: три колонки FCFS, OR-Tools, диспетчеры.

## 7. Перепланирование

`replan.apply(state, event) -> (plan, diff)`:
- `now` равно времени события.
- Визиты со стартом раньше `now` закрепляются за своим инженером в своём порядке; инженер стартует из точки последнего закреплённого визита в его время окончания.
- `engineer_unavailable`: конец смены инженера равен `now`, его незакреплённые визиты возвращаются в пул.
- `cancel`: заявка помечается cancelled и исключается. `restore`: снова active. История событий хранится в состоянии сеанса, «вернуть» это событие, а не откат.
- `urgent`: заявка добавляется с приоритетом urgent, геокодируется, матрица дополняется одной точкой.
- Вызывается тот же солвер с предыдущим планом как warm start. `diff.compute(old, new)` считает перемещения, изменения порядка, сдвиги времени.
- Базовый FCFS пересчитывается на той же текущей задаче после каждого события, чтобы сравнение с базой оставалось честным. План диспетчеров остаётся исходным ориентиром дня.

## 8. Объяснения

`explain.build(plan, problem)` для каждой заявки:
- Назначенная: инженеры, прошедшие фильтр навыка и транспорта; причины отсева остальных (нет навыка, нет транспорта, не помещается в смену, недоступен); приезд относительно окна и запас; дельта километров до лучшей альтернативной вставки у другого допустимого инженера (считается cheapest-insertion по матрице, не солвером); факторы, повлиявшие на выбор (меньше инженеров, короче пробег, срочность).
- Неназначенная: один из четырёх reason_code ТЗ (`no_free_engineer_in_window`, `no_skill`, `no_transport`, `does_not_fit_window_or_shift`) или `address_not_found` плюс конкретика («ближайший инженер с навыком Аварийные работы освобождается в 16:40»).
Текст собирается шаблонами на русском. LLM не участвует.

## 9. API

Полный контракт с JSON-схемами и эндпоинтами: `docs/superpowers/specs/2026-09-15-api-contract.md`. Коротко: загрузка с фоновым предподсчётом и опросом статуса, построение плана, события, объяснение заявки, геометрия маршрута, чат и предложения (План 4). Ошибки возвращают `{"detail": "текст на русском"}`.

## 10. Фронт

React, Vite, TypeScript, zustand, Яндекс Maps JS API v3 как подложка с маркерами и полилиниями (геометрия своя из OSRM, чтобы карта и солвер совпадали). Экраны:

- Пустое состояние: загрузка файла, после загрузки отчёт предподсчёта и кнопка «Спланировать».
- Основной экран: слева карта Москвы с областью; справа список заявок с назначенным инженером, временем приезда, статусом; фильтр по инженеру подсвечивает его маршрут. Сверху полоска метрик с тремя колонками (FCFS, наш, диспетчеры). Внизу правой панели кнопки событий: срочная заявка (форма), отменить/вернуть (в строке заявки), инженер недоступен (выбор инженера и времени). Время события по умолчанию равно текущему времени плана, редактируется в диалоге.
- Карточка заявки: обоснование из раздела 8, альтернативы.
- Вкладка «Таймлайн»: Gantt по инженерам, визиты полосками, окна рамками, закреплённые визиты отмечены.
- После события: баннер с diff, переключатель до/после, перемещённые заявки подсвечены на карте и в списке.
- Вкладка «Рекомендуемые изменения»: текстовое поле, карточки предложений с approve/reject, кнопки approve all и reject all, у применённых показан diff.
- Вкладка «Неназначенные»: список с причинами.

## 11. LLM-окно

OpenAI-совместимый API (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` из env). Function calling с инструментами `propose_urgent_request`, `propose_cancel`, `propose_restore`, `propose_engineer_unavailable`, `ask_clarification`; фолбэк для провайдеров без tool use: JSON-схема в промпте и валидация pydantic. В контекст передаются инженеры (id, имя) и заявки (id, адрес, инженер), чтобы модель резолвила имена и адреса. Модель только предлагает: результат это `Proposal` со статусом pending, применение только через approve пользователем. Без ключа вкладка показывает заглушку, кнопки событий работают.

## 12. Тестирование

Pytest в `backend/tests/`:
- Ограничения: по одному тесту на навык, транспорт, окно, смену, с ручными мини-задачами на 2-3 заявки. Проверка через `feasibility.check` на планах обоих солверов.
- FCFS: ручной пример из ТЗ, где последовательное распределение хуже оптимального.
- Перепланирование: по тесту на каждое из четырёх событий, проверка закрепления прошлого и корректности diff.
- Объяснения: reason_code для каждой из четырёх причин.
- Синтез: `prepare` на реальных файлах из `data/` даёт бандл без ошибок и проходит самопроверку.
- Ingest: cp1251, мусорные строки, строка офиса, дубли ID.
Frontend: vitest на store и на рендер diff, без e2e.

- Бандл региона один файл `bundle.json` вместо пяти.
- Добавлена причина `address_not_found`.
- OR-Tools 9.15: навыки через `VehicleVar().SetValues`, warm start принимает индексы. Прототип модели прошёл на 3 инженерах и 6 заявках.
- OSRM: образ `ghcr.io/project-osrm/osrm-backend:v26.9.0-debian`, выгрузка ЦФО 835 МБ режется osmium по bbox.
- Базовый FCFS пересчитывается после каждого события.
- Строки контрольного и синтетического файлов совпадают по индексу во всех регионах, проверено. В контроле Юго-востока дубль ID: отменённая и повторно выполненная заявка.
